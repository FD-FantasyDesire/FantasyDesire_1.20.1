# 超新星汇聚性能记录

## 2026-10-02 优化更新

已实施云团半分辨率积分、原分辨率深度感知重建、空腔跳步、外轮廓/零密度提前返回和包围域优先剔除。粒子、冲击壳、星核仍为原分辨率。云团默认 `CloudOpacity=0.5`，预乘 RGB 和 alpha 同时缩放，积分密度及默认 56 步保持不变。

同一隐藏 GPU 会话依次加载本次修改前的冻结三件套（before）、当前全分辨率（full）及当前半分辨率（half）。复用下文相机、尺度、种子和布局，每组 3 帧预热、9 帧测量；48 组，共 576 次预热/测量 render 请求。GPU 时间包含缩小积分与原分辨率合成两个 draw；不包含场景和深度复制。9 帧的 P95 仍为最大值，仅作为短时波动参考。

before 云团不透明度为原来的 100%，full/half 为 50%，同时存在颜色分层合成变化；这项前后对比衡量最终版本整体成本，不能将全部收益归因于降分辨率。full/half 才是相同算法、相同透明度的分辨率对照。50% 在积分结束后应用，没有通过修改密度让积分更早退出。

| 布局 / 阶段 | 修改前 | 当前全分辨率 | 当前半分辨率 |
| --- | --- | --- | --- |
| 分散 / 云团 | 42.96 / 45.67 | 33.19 / 35.28 | 22.50 / 23.21 |
| 分散 / 消散 | 54.12 / 55.42 | 33.45 / 35.06 | 19.01 / 20.29 |
| 重叠 / 云团 | 58.92 / 64.95 | 34.70 / 35.29 | 35.81 / 38.88 |
| 重叠 / 消散 | 64.08 / 70.35 | 35.01 / 39.15 | 35.82 / 39.27 |

八实例分散云团阶段从 42.96 ms 降到 22.50 ms，约降低 48%；消散从 54.12 ms 降到 19.01 ms，约降低 65%。重叠云团从 58.92 ms 降到 35.81 ms，约降低 39%。仍不满足将整个游戏维持在 16.67 ms 帧预算内的要求。

**半分辨率并非所有场景都更快。** 单实例 1080p 云团：full=5.19 ms、half=5.48 ms；八实例重叠：full=34.70 ms、half=35.81 ms。多实例重叠放在地形深度交界时，精确重算与放大成本会抵消低分辨率收益；少量、小覆盖实例可选 `full.preview.json`。本轮默认压测入口使用半分辨率，后续需要按覆盖面积、深度边缘与并发量决定质量，不能承诺固定 4 倍加速。

## 场景和方法

- 分辨率 1280×720 / 1920×1080；相机 yaw=25°、pitch=12°、distance=24、FOV=55°。
- EffectCenter=(0,3.5,0)，EffectScale=0.65，种子 17+131×槽号，均同时出生；爆炸倒计时 2.8 秒。
- 分散布局列数 ceil(sqrt(N))，X/Z 间距 5 格；重叠布局间距 0。单实例的两种布局相同。
- 每组 3 帧预热、5 帧测量，记录中位数及 P95；5 个样本下 P95 等于最大值，不能当作长期统计。复测建议用 7–50 帧。
- 汇聚 1.7 秒、膨胀 3.1 秒、云团 3.75 秒、消散 5.3 秒；体积 32/56/80 步，尾迹统一 18 段。
- 每个片元遍历活动实例，包围球求交剔除无贡献实例；各实例有独立种子和深度裁剪，单个批次 draw。该测试没有 Java 多批次成本。
- 主测试和补测消散阶段各运行一次隐藏进程，共 192 组、1536 次预热/测量绘制。原始采样见 [benchmark-results.json](benchmark-results.json)。

## 结论与限制

单实例、56 步的 1080p 云团阶段约 6.82 ms；八实例分散约 43.54 ms，重叠约 54.91 ms。单效果已消耗可观预算，4–16 个同时触发不能视为满足 60 FPS（整帧预算 16.67 ms），这些数字也不能直接取倒数当作游戏帧率。

消散阶段可能更慢：八实例分散/重叠在 1080p、56 步分别约 53.39 / 67.98 ms。此时半径更大，稀薄云团很难达到透射率提前退出阈值，因此“看起来快消失”不等于 GPU 便宜。默认单实例预览更靠近相机、尺度为 1，其成本不能与本表尺度 0.65 的远距离测试直接互换；相机进入云团时覆盖面积接近全屏，首轮单帧可达约 50 ms。

32 步能降低云团积分成本，但不降低汇聚阶段的有限贝塞尔尾迹投影/距离计算。八实例汇聚仍约 44 ms，说明只降低体积精度不能解决所有阶段的并发问题。32 步近距离比 56/80 步更容易出现采样纹理，已导出同场景质量对照。

大批次、80 步的部分数字出现平台甚至比 56 步低；单实例相同布局也有差异。笔记本 GPU 的时钟/功耗状态、驱动调度、分支覆盖及短采样都有影响，测量未锁定频率、温度或其他进程负载。不要据此宣称高步数更快或精确线性扩展。

当前按实例槽序透明合成，没有跨实例联合体积积分。重叠用例验证的是实际多个种子的计算和合成成本，不是任意相交云团的物理正确融合；实际游戏还要加入独立实例提交和透明排序成本。

## 后续优化方向

1. 将三维轨迹与有限尾迹改为 Java 生成带状网格，粒子头/星核使用 billboard，移除全屏每片元重复 14×18 段投影与求距。
2. 体积使用包围盒/球代理或屏幕矩形限制覆盖，结合质量分级、距离裁剪和活动实例预算。32 步只是折中，不是并发问题的完整解法。
3. 采用低分辨率积分与深度感知重建，并在消散期按密度/贡献缩减采样；接入前比较颜色和边缘，避免提前消失或穿透。
4. 用相同场景复测优化前后 GPU 时间，再在 Minecraft 无光影/有光影及多实例战斗中测整帧。当前交付验证报告，不宣称完成游戏性能优化。
